```python
import torch
import nnsight
import nnterp
from nnterp import StandardizedTransformer

model = StandardizedTransformer("openai-community/gpt2", device="cpu", dispatch=True, attn_implementation="eager")
prompt = "The Eiffel Tower is in the city of"
n = len(model.tokenizer.encode(prompt))          # 10
```

## The values under `generate`

`model.generate(prompt, max_new_tokens=N)` runs one forward for the prompt and
one per new token, and every standard value is served once per forward. So
`layer_output` on the prompt call is `[batch, prompt_len, hidden]` and on a
decode step `[batch, 1, hidden]`; `next_token_probs` is the distribution that
produced each step's token; `input_ids` is the one token the step is fed.
`tracer.iter[...]` binds a stretch of the block to chosen steps, and
`tracer.result` is the generated ids. How `generate` and `tracer.iter` work is
nnsight's (the `nnsight` skill, generation reference); this is what nnterp's
values look like under them.

```python
resid, probs = [], []                              # made outside the block: a name bound inside does not survive it
with model.generate(prompt, max_new_tokens=3, do_sample=False) as tracer:
    for step in tracer.iter[:3]:                   # steps 0, 1, 2
        resid.append(model.layers[6].layer_output.save())
        probs.append(model.next_token_probs.save())    # the distribution this step samples from
    ids = tracer.result.save()                     # [batch, prompt_len + 3]

assert [tuple(r.shape) for r in resid] == [(1, n, 768), (1, 1, 768), (1, 1, 768)]
assert ids.shape == (1, n + 3)
assert all(probs[i].argmax(-1).item() == ids[0, n + i].item() for i in range(3))   # greedy: each argmax is the appended token
print(model.tokenizer.decode(ids[0, n:]))
```

| value | prompt call (step 0) | decode step |
|---|---|---|
| `model.input_ids`, `model.input_size` | `[batch, prompt_len]` | `[batch, 1]`: the token generated by the previous step |
| `layer_output`, `attention_output`, `mlp_output`, `token_embeddings` | `[batch, prompt_len, hidden]` | `[batch, 1, hidden]` |
| `attention_queries`, `attention_head_outputs` | `seq == prompt_len` | `seq == 1` |
| `attention_keys`, `attention_values` | `[batch, kv_heads, prompt_len, head_dim]` | `[batch, kv_heads, prompt_len + step, head_dim]`: the cache |
| `attention_scores`, `attention_probabilities` | `[batch, heads, prompt_len, prompt_len]` | `[batch, heads, 1, prompt_len + step]` |
| `model.logits` | `[batch, prompt_len, vocab]` | `[batch, 1, vocab]` |
| `model.next_token_probs` | `[batch, vocab]` | `[batch, vocab]` |

**Picking steps.** `tracer.iter[k]` binds the body to step `k`, `tracer.iter[:n]`
to the first `n`, `tracer.iter[1:]` to every decode step. A read outside any loop
binds to step 0. A write at a step reaches that step and everything after it:

```python
with model.generate(prompt, max_new_tokens=3, do_sample=False) as tracer:
    for step in tracer.iter[1]:
        step_ids = model.input_ids.save()                  # [batch, 1]: the token step 0 produced
        one = model.layers[6].layer_output.save()          # [batch, 1, hidden]
        model.layers[6].layer_output[:] = 0                # steps 1 and 2 change; step 0's token does not
    edited = tracer.result.save()

assert step_ids.shape == (1, 1) and one.shape == (1, 1, 768)
assert torch.equal(edited[0, : n + 1], ids[0, : n + 1])   # the prompt and step 0's token are untouched
```

**Read order within a step** follows the forward like in a trace: `input_ids`
first, a block's `self_attn.*` and `mlp.*` before its `layer_output`, `logits`
and `next_token_probs` last. Inside `tracer.iter` a misplaced read does **not**
raise: it binds the same location on the *next* step, so a per-step list comes
back shifted by one (the pattern read after `attention_output` is step `k+1`'s),
and the only symptom is a final warning blaming the loop bound. Check each
step's shapes (`[batch, 1, ...]` on a decode step, the cache length on the key
axis) when a per-step result looks off.

**`tracer.result` after an open loop is never bound.** `tracer.iter[:]` and
`tracer.all()` end by outrunning the run, and the statements after the loop do
not execute (nnsight warns, and does not raise). Use a bounded `tracer.iter[:N]`
with `N == max_new_tokens`, and `min_new_tokens=N` when an EOS could stop the
run early. Decoding follows the checkpoint's `generation_config`; pass
`do_sample=False` for a deterministic run.

On a recurrent block a decode step runs the single-step kernel and
`linear_attn.state_input` carries the previous step's `state_output`; on Mamba-1
and Mamba-2 read `state_output` before `attention_head_outputs` there. On a
mixture the routing values are `[batch, 1, top_k]` per decode step. See
[recurrent-mixers.md](recurrent-mixers.md) and
[mixture-of-experts.md](mixture-of-experts.md).

## `nnterp.nnsight_utils`: activations over prompts

Probing, steering vectors and logit lenses start the same way: the residual
stream at one position of every prompt, at chosen blocks, stacked. The helpers
read the standard values, so one call runs on every family (the names are
nnterp's):

| function | returns |
|---|---|
| `get_token_activations(model, prompts=None, layers=None, get_activations=None, remote=False, idx=None, tracer=None)` | `[num_layers, num_prompts, hidden]` at position `idx` (default `-1`) of every prompt, on the CPU |
| `collect_token_activations_batched(model, prompts, batch_size, layers=None, ..., tqdm=None, use_session=True)` | the same over batches, concatenated on the prompt axis |
| `collect_last_token_activations_session(model, prompts, batch_size, ...)` | the same batches inside one `model.session`, so a remote run is one request |
| `compute_next_token_probs(model, prompt, remote=False)` | `model.next_token_probs` per prompt, `[num_prompts, vocab]` on the CPU |

```python
from nnterp.nnsight_utils import get_token_activations, collect_token_activations_batched, compute_next_token_probs

acts = get_token_activations(model, [prompt, "Hello"], layers=[4, 8])
assert acts.shape == (2, 2, 768) and acts.device.type == "cpu"     # [num_layers, num_prompts, hidden]

with model.trace(prompt):
    ref = model.layers[4].layer_output[0, -1].save()
assert torch.allclose(acts[0, 0], ref.cpu(), atol=1e-4)           # acts[i, j] is layers[layers[i]].layer_output[j, -1]

batched = collect_token_activations_batched(model, [prompt, "Hello", "Hi there"], batch_size=2, layers=[4, 8])
assert batched.shape == (2, 3, 768)

dist = compute_next_token_probs(model, [prompt, "Hello"])
assert dist.shape == (2, model.vocab_size)
assert model.tokenizer.decode(dist[0].argmax()) == " Paris"
```

`get_activations(model, layer) -> Tensor` swaps the value collected: any
standard value with a sequence axis in position 1 works
(`lambda m, i: m.layers[i].self_attn.attention_output`); softmax attention's
queries, keys and values put it at 2 and need a lambda that reshapes first.
`layers` indexes the result: `layers=[4, 8]` gives rows 0 and 1. With
`tracer=`, the helper reads inside your open trace and the result is a live
tensor for you to `.save()`.

**Padding.** `idx=-1` is each prompt's last token only under left padding; a
negative `idx` with a tokenizer that pads right raises `ValueError` before
anything runs, and a positive `idx` needs right padding. GPT-2's tokenizer on
this transformers already pads left with `<|endoftext|>` as the pad token, which
is why the calls above work as is; set it explicitly when it is not:

```python
padded = StandardizedTransformer("openai-community/gpt2", tokenizer_kwargs={"padding_side": "left", "pad_token": "<|endoftext|>"})
assert padded.tokenizer.padding_side == "left"          # tokenizer_kwargs sets attributes on the loaded tokenizer

model.tokenizer.padding_side = "left"                   # or set them on a loaded model
with model.trace([prompt, "Hello"]):
    mask = model.attention_mask.save()
    probs = model.next_token_probs.save()

assert mask[1, :n - 1].sum() == 0                       # "Hello" is left-padded: zeros first
assert model.tokenizer.decode(probs[0].argmax()) == " Paris"
```

## `nnterp.prompt_utils`: target-token mass over prompts

How much probability does the model put on *these* words next?
`get_first_tokens` turns words into the token ids a model would emit for them,
`Prompt` pairs a prompt with named sets of those ids, and `run_prompts` runs many
prompts in batches and returns each target's probability mass per prompt.
Everything reads `model.next_token_probs`.

```python
from nnterp.prompt_utils import Prompt, get_first_tokens, run_prompts

ids_ = get_first_tokens(["Paris", "London"], model)
assert [model.tokenizer.decode([i]) for i in ids_] == ["Paris", " Paris", "London", " London"]   # both spellings, deduplicated

prompts = [
    Prompt.from_strings("The capital of France is", {"correct": "Paris", "wrong": ["London", "Berlin"]}, model),
    Prompt.from_strings("The capital of Germany is", {"correct": "Berlin", "wrong": ["London", "Paris"]}, model),
]
assert prompts[0].has_no_collisions()                   # no token id belongs to two targets

mass = run_prompts(model, prompts, batch_size=32)
assert mass["correct"].shape == (2, 1)                  # [num_prompts, layers]; the next-token distribution is one "layer"
assert (mass["correct"] > mass["wrong"]).all()
```

`get_first_tokens` uses `model.add_prefix_false_tokenizer` (the checkpoint's
tokenizer with `add_prefix_space=False`) so `"word"` and `" word"` stay
different tokens; given a raw tokenizer that adds a prefix space it warns and
falls back to a pear trick, and raises `TokenizationError` when that fails too.
Decode `target_tokens` before trusting a run: on a byte-pair vocabulary a rare
word's first token is a fragment, and the mass then counts every continuation.
For a single target logit, take `model.tokenizer(" Paris", add_special_tokens=False).input_ids`
and assert it has one element; `tokenizer.encode(" Paris")[0]` is the BOS token on
Llama-3 and Gemma.

`model.get_topk_closest_tokens` and `model.probs_to_dict` return
`{decoded string: probability}`: byte tokens that decode to the same `'�'`
collapse into one entry (half the rows on a Japanese GPT-2 prompt). Take
`probs.topk(k)` and the ids when the vocabulary is byte-level and the text is not
ASCII.

`run_prompts(..., get_probs_func=f, func_kwargs={...})` takes a function
`f(model, batch, remote=False, **kwargs) -> [batch, layers, vocab]`, which is how
the layer axis becomes something: the logit lens at chosen blocks through
`model.project_on_vocab`:

```python
def lens_probs(model, batch, remote=False, layers=None):
    with model.trace(batch, remote=remote):
        rows = [model.project_on_vocab(model.layers[i].layer_output)[:, -1].softmax(-1) for i in layers]
        out = torch.stack(rows, dim=1).cpu().save()          # [batch, len(layers), vocab]
    return out

lens_mass = run_prompts(model, prompts, batch_size=32, get_probs_func=lens_probs, func_kwargs={"layers": [4, 8, 11]})
assert lens_mass["correct"].shape == (2, 3)                  # the target's mass at blocks 4, 8 and 11
```

Batched runs need left padding for the same reason as above. `remote=True`
passes through to every trace, and a `get_probs_func` must forward it.

## `remote=True`: the contract

`remote=True` on a `StandardizedTransformer` is nnsight's remote trace with
nnterp's names and values in the block; the `remote` skill covers NDIF itself.
What nnterp adds:

- **The request reaches a plain deployment.** The model key names
  `TransformersModel`, not `StandardizedTransformer`, so every checkpoint NDIF
  serves is reachable without the server deploying anything nnterp-specific.
- **The server needs nnterp installed, at the client's version.** The block is
  re-run against the client's envoy tree, which carries the family's envoy
  classes by reference. Do not ship nnterp by value: `nnsight.register(nnterp)` is
  for local helper modules, an installed package is pickled by reference anyway,
  and an `eproperty` cannot be pickled by value. Register your own helper module
  if the block calls one.
- **Source-located values resolve against the server's transformers.** A server
  on another release fails with `SourceNotAvailable` server-side, not
  `Unavailable` client-side. `support()` and the `Unavailable` check run on your
  meta model: load the client with the `attn_implementation` the deployment
  runs. Kernel routing (`route_kernels`) and `chunk_per_token` change *your*
  process and model; treat a recurrent mixer's `state`/`states` as unavailable
  remotely.
- **Save small things**; every `.save()` is downloaded. Slice inside the block.

`remote="local"` runs the serialize, deserialize and execute path in-process
against a dispatched model: the way to check that a block, its aliases and its
values survive the round trip before submitting it.

```python
with model.trace(prompt, remote="local"):
    pattern = model.layers[3].self_attn.attention_probabilities.save()
    local_logits = model.logits.save()

with model.trace(prompt):
    plain_logits = model.logits.save()

assert pattern.shape == (1, 12, n, n)
assert torch.allclose(local_logits.to(plain_logits.device), plain_logits)
```
